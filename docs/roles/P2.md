## Concepts to teach P2 first (5 minutes, simple words)
- Circuit: a set of equations (constraints) that must all be true. We write it in Circom.
- Witness: all the numbers that make the equations true, including private ones.
- Public vs private inputs: public inputs are visible to everyone (and to the contract). Private inputs stay on our laptop.
- Groth16: the proof system. It needs a setup: a public "powers of tau" file (phase 1, downloaded) plus our own quick phase 2. That produces a proving key (.zkey) and a verification key.
- Verifier.sol: a contract generated from the zkey that checks proofs on-chain.
- IMPORTANT: if the circuit changes, the zkey AND Verifier.sol change, and P3 must redeploy. So the circuit is FROZEN at 3:00 AM.

## Step 3: Real circuit (zk/circuits/autoevolve.circom)
Includes: circomlib/circuits/comparators.circom, bitify.circom, poseidon.circom (compile with `-l zk/node_modules`).
Declare signals IN THIS ORDER so the public signals come out in PLAN.md 3.5 order:
- `signal input m[3][4];` (public)
- `signal input promptCommitment;` (public)
- `signal input snapshotHash;` (public)
- `signal input agentWallet;` (public)
- `signal input taskId;` (public)
- `signal input promptHash;` (private)
- `signal input salt;` (private)
- main: `component main {public [m, promptCommitment, snapshotHash, agentWallet, taskId]} = AutoEvolve();`
- No output signals. That keeps the public signal order simple.

Constraints:
1. Each metric: Num2Bits(7) (forces it under 128), then LessEqThan(7) against 100, with out === 1.
2. S[k] = 50*m[k][0] + 20*m[k][1] + 15*m[k][2] + 15*m[k][3] for k = 0, 1, 2. Weights are CONSTANTS in the circuit; this is the pre-committed formula.
3. LessThan(14): S[0] < S[1] and S[1] < S[2]. (Max score 10000 < 16384.)
4. Poseidon(2)(promptHash, salt) === promptCommitment.
5. Dummy squares for snapshotHash, agentWallet and taskId (e.g. `walletSq <== agentWallet * agentWallet;`). WHY: in Circom, a public input that appears in no constraint may not be bound to the proof, so someone could swap it. Tornado Cash uses the same trick.

Teach P2 each constraint as you write it: what it prevents and how to explain it.

## Step 5: zk/prove.js runs/<id>
1. Read run.json (raw bytes AND parsed), secret.json and evaluator.json from the run folder.
2. Cross-checks (exit with a clear error if any fail):
   - evaluator.metrics equals the metrics in run.json
   - BigInt(ethers.keccak256(raw run.json bytes)) % P equals evaluator.snapshot_hash
3. promptCommitment = Poseidon([promptHash, salt]) using circomlibjs buildPoseidon (F.toString for decimal).
4. Input: m (3x4), promptCommitment, snapshotHash, agentWallet = BigInt(address), taskId, promptHash, salt. Everything as decimal strings.
5. `snarkjs.groth16.fullProve(input, zk/out/autoevolve.wasm, zk/out/autoevolve_final.zkey)`, then verify locally with verification_key.json.
6. Assert publicSignals.length == 16, [12] == promptCommitment, [13] == snapshotHash, [14] == agentWallet, [15] == taskId.
7. Use `snarkjs.groth16.exportSolidityCallData(proof, publicSignals)` to get the Solidity format (it swaps pB's coordinates for you; NEVER format by hand). Parse it, convert all values to decimal strings, write proof.json (PLAN.md 3.3). Append events.jsonl (actor "prover").
8. End with process.exit(0). snarkjs leaves worker threads open, so without this the script hangs.
- If the scores don't increase, witness generation fails with an assertion error. Catch it and print "CANNOT PROVE: score did not improve". That's cheat demo #1.

## How P2 explains it to judges
"Our circuit has the scoring formula baked in, so nobody can change the weights after the fact. It proves V1 < V2 < V3 under that formula and that we know the secret system prompt behind a public commitment, without revealing it. The contract only pays if the proof is valid AND the independent evaluator signed the same metrics. Watch: when an agent invents its own scores, the proof is mathematically valid, but the contract still rejects it."

## Likely judge questions
- Why Circom/Groth16 and not SP1/EZKL? Tiny, fast proofs, cheap on-chain verification, and snarkjs generates the Solidity verifier. EZKL is for neural-network inference; SP1 would add a Rust toolchain for no benefit at this circuit size.
- Trusted setup? Phase 1 comes from the public Hermez ceremony. Phase 2 we ran ourselves with one contributor, which is fine for a hackathon. Production would use a multi-party ceremony.
- If the metrics are public, why ZK at all? It enforces the pre-committed formula on-chain as a reusable proof, hides the system prompt while proving we know it, and binds the memory snapshot and agent wallet into one proof. We don't claim it proves the LLM was honest.
- What are the dummy squares? They force every public input to be bound to the proof, so nobody can swap the wallet or snapshot.
