## Step 8: pipeline/submit.py --run runs/<id>
1. Load run.json bytes, evaluator.json, proof.json, plus the deployment and the agent key (A or B from run.json's "agent" field).
2. Sanity checks before spending gas:
   - snapshot_hash_of_file == evaluator.snapshot_hash == pubSignals[13]
   - pubSignals[14] == agent address
   - pubSignals[15] == task_id
3. Upload run.json to get the CID.
4. FIRST an eth_call (`.call({"from": agent})`) to surface any revert reason for free. Then send the real transaction, wait for the receipt, parse ImprovementVerified to get record_id.
5. Write receipt.json, append events.jsonl ("upload", "submit", "verified"), print the explorer link + IPFS link + reward.

## How P3 explains it to judges
"The contract is the referee and the piggy bank. It pays only when four things hold: the ZK proof is valid, the independent evaluator signed the same metrics, the proof belongs to the wallet submitting it, and that agent hasn't been paid for this task before. It then records the IPFS CID and snapshot hash publicly, so any agent can download the memory and check it wasn't changed."

## Likely judge questions
- How do you verify the IPFS memory? The proof includes the snapshot hash; the contract stores it with the CID; anyone can download the CID and re-hash it. Agent B does exactly that.
- What stops front-running? The proof contains the agent's wallet, and the contract requires msg.sender to match.
- Why not check the CID on-chain? A CID is a multihash format that's expensive to check in a circuit or contract, so we commit a Keccak hash of the same bytes instead.
