# P1: Agent engineer, explained in plain English

## The big picture
1. **Qwen** (the generator) writes Python code for a task. That is **V1**.
2. The **evaluator** runs hidden tests on it in a sandbox and computes 4 numbers (0-100). Code computes the
   score, never an AI.
3. **DeepSeek-R1** (a *different* model, the critic) reads what failed and writes a review.
4. Qwen rewrites the code using the review, giving **V2**. V2 is only accepted if its score is *strictly
   higher*. Then the same happens again for **V3**.
5. Everything is saved in `runs/<run_id>/run.json`, the public record that goes to IPFS.
6. **Agent B** (a separate agent with its own wallet) later reads past runs from the blockchain + IPFS,
   checks that they were not tampered with, and uses their lessons on new tasks.

## The 4 metrics and the score
| Metric | How it is computed |
|---|---|
| tests_passed | % of the 8 "core" hidden tests passed (integer division) |
| edge_cases | % of the 8 "edge" hidden tests passed |
| lint | 100 - 10 per ruff warning (E, F, W rules; long lines ignored) |
| simplicity | 100 - 10 per complexity point above 5 (radon cyclomatic complexity) |

**Score = 50×tests + 20×edge + 15×lint + 15×simplicity**, from 0 to 10000. These weights are frozen and
are also built into P2's ZK circuit.

## What each file does
### tasks/
- `tasks.json`: list of the 4 tasks (all are "log_parsing").
- `t1/spec.md` … `t4/spec.md`: the exact rules the code must follow. The generator only ever sees this.
- `t1/tests.json` … `t4/tests.json`: the HIDDEN tests (8 core + 8 edge each). Their hash goes on-chain, so
  **these files must never change after P3 registers them** (task 1 frozen 2:30 AM, tasks 2-4 at 5:30 AM).
- `t*/reference.py`: our own correct solution. It proves every test suite can be scored at 10000.
- `.gitattributes`: stops git from changing line endings (that would change the on-chain hash).

All 4 tasks share one log-line format (`DATE TIME [LEVEL] message`). That is deliberate: what Agent A
learns on task 1 (strip whitespace, `WARNING` means `WARN`, check time ranges, ...) really helps on 2-4.

### evaluator/
- `sandbox.py`: runs the untrusted code in a separate process with a 10-second limit and an environment
  containing **no API keys** (only `PATH`, `PYTHONHASHSEED`, and `SYSTEMROOT` on Windows). With
  `USE_DOCKER=1` it uses a Docker container with no network. Only the test *inputs* go into the sandbox;
  the expected answers stay outside, so the code cannot cheat by reading them.
- `runner.py`: the tiny script that runs inside the sandbox and records what the function returned.
  A random nonce stops the code from faking the results file.
- `metrics.py`: turns results + ruff + radon into the 4 integers and the score.
- `__init__.py`: `evaluate(task_id, code)`. P2's evaluator signature step re-runs this.
- `selftest.py`: `python -m evaluator.selftest` proves all of this (see "Proof it works").

### agent/
- `llm.py`: talks to Featherless. Every request and response is hashed (keccak) and cached in
  `agent/.cache/`, so a run can be reproduced from its record. `--mock-llm` uses canned answers from
  `mock_responses/` so development costs no credits.
- `prompt_builder.py`: every prompt in one place. The critic never sees the expected answers or our secret
  system prompt.
- `run.py`: the loop. Writes `run.json` (public), `secret.json` (private: prompt hash + salt for the ZK
  proof) and `events.jsonl` (live log for the dashboard).
- `check_run.py`: verifies a run folder (canonical bytes, V1<V2<V3, hash chain, no secrets, re-evaluation).
- `memory.py`: Agent B's memory. It reads records from the contract, downloads each run from IPFS and
  **rejects any whose bytes don't match the hash stored on-chain**.
- `agent_b.py`: Agent B. It prints `INJECTING LESSON: ...` and runs the same loop with those lessons.
- `benchmark.py`: V1 without memory vs V1 with memory on tasks 2-4, saved to `runs/benchmark.json`.
- `smoke.py`: one real call per model (checkpoint 1).
- `prompts/system_prompt.txt`: SECRET, gitignored. Only its hash leaves the laptop.
- `samples/run.sample.json`: an example run.json for P2/P3/P4 (no secrets in it).
- All hashing goes through P3's `common/hashing.py`, and wallet/registry addresses come from `common/config.py`
  (`addresses()["agent_A"]`, `load_deployment()["registry"]`). P1 never re-implements either.
- In `--mock-llm` runs, `models.generator` / `models.critic` start with `mock/`, so a mock run can never be
  passed off as real model output. Real runs write exactly `Qwen/Qwen2.5-Coder-32B-Instruct` and
  `deepseek-ai/DeepSeek-R1-0528`.

## Commands
```
python -m evaluator.selftest                          # evaluator proof
python -m agent.smoke                                  # one real call per model
python -m agent.run --task 1 --agent A [--mock-llm]    # the loop; last line = run folder
python -m agent.check_run runs/<run_id>                # verify a run
python -m agent.agent_b --task 2 [--mock-llm] [--mock-chain]
python -m agent.benchmark --tasks 2 3 4 [--mock-llm] [--mock-chain]
```
Exit code 0 only when the status is `improved`. Other statuses: `too_easy` (V1 already perfect: the task
needs harder edge rules) and `failed_no_improvement` (3 revision attempts never beat the previous score).

## Proof it works (mock mode, 2026-10-30)
- Evaluator: all 4 reference solutions score 10000. A sloppy solution scores 8290 and fails 5 edge cases.
  Identical results on repeat runs. The sandbox sees no keys. An infinite loop times out. A forged results
  file is rejected.
- Loop on task 1: 9000 → 9250 → 10000. Changelog: "V2: fixed edge_2, edge_4, edge_5, edge_7; simplicity
  100 -> 50", then "V3: simplicity 50 -> 100".
- Agent B on task 2 (simulated chain): rejects a tampered record, injects 3 verified lessons,
  9590 → 9850 → 10000.
- Benchmark (mock): average V1 score 8740 without memory → 9423 with memory, 3/3 tasks improved.
  **These are mock numbers. Report the real numbers from real runs at the demo.**

## How to explain this to judges (3 sentences)
"Our agent never grades itself: Qwen writes the code, hidden tests in a sandbox produce the score with
plain integer math, and a different model, DeepSeek-R1, only writes the critique. Each version must score
strictly higher than the last, and the automatic changelog shows exactly which hidden tests each version
fixed. Agent B then reads Agent A's verified lessons from the blockchain and IPFS, rejects anything whose
hash doesn't match the chain, and starts out better because it avoids Agent A's mistakes."

## Likely judge questions
- **Why two models?** A model judging its own work is biased. Here tests produce the score, and the critic
  is a different model.
- **Is temperature 0 deterministic?** Not fully. So we hash and cache every request and response, and the
  run is reproducible from its record.
- **Is running AI-written code safe?** It runs in a separate process with a timeout and no secrets in its
  environment (and no network with Docker). It never sees the expected answers.
- **Couldn't the agent memorise the tests?** Partly: the critic sees failing *inputs* (not expected
  outputs). That's a known limitation; production would use a separate held-out test set.
- **Why does V3 sometimes only improve simplicity or lint?** The score has four parts. Cleaner code is a
  real, measurable improvement, and the changelog says exactly which part improved.
