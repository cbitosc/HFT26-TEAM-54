# P4 explained: dashboard, demo, pitch

## What the dashboard is
A website that runs on the demo laptop (`cd dashboard && npm run dev`, then open localhost:3000).
It reads the files that the other three people's scripts write, and shows them live (it re-reads every 3 seconds).
It never changes any file and never holds a private key.

## What each file does (plain English)

| File | What it does |
|---|---|
| `dashboard/lib/repo.js` | Finds the run folders in `runs/` and `backup/` and reads their 5 files. If there are no runs yet it shows the example files from `schemas/examples/`. Refuses run names with `/` or `..` so nobody can read other files through the URL. |
| `dashboard/lib/model.js` | Works out "what has happened so far" for one run: which versions are done, which retries were rejected, which of sign / prove / upload / submit are finished. Works even while the run is still going (before `run.json` exists) by reading `events.jsonl`. Also labels the 16 public signals. |
| `dashboard/app/api/runs/route.js` | `/api/runs`: the list of runs (id, task, agent, status, scores, which steps are done). |
| `dashboard/app/api/runs/[id]/route.js` | `/api/runs/<id>`: everything about one run. |
| `dashboard/app/api/chain/route.js` | `/api/chain`: asks the smart contract how many records it has and reads each one (task, agent, CID, scores, time), plus the escrow balance and the transaction hashes. Uses the `viem` library. Caches for 4 seconds so we do not spam the RPC. |
| `dashboard/app/api/extras/route.js` | `/api/extras`: the Agent B benchmark and the cheat-demo results. |
| `dashboard/app/page.js` | The page: header, the 4 tabs, light/dark switch, "follow latest". |
| `dashboard/components/ExecTree.js` | The execution tree drawing (library `@xyflow/react`): V1 → V2 → V3, failed retries as red side branches, then sign → prove → upload → on-chain. Green = done, blue pulsing = running, red = rejected, dashed = not yet. |
| `dashboard/components/DiffPanel.js` | Side-by-side code diff between versions (library `react-diff-viewer-continued`), the critic's feedback that caused the change, the changelog and the lessons. |
| `dashboard/components/ProofPanel.js` | Big Verified / Rejected badge, the 16 public signals with names, three checks (scores really go up with the fixed weights; proof metrics = signed metrics; prompt hidden behind a commitment), tx + IPFS links, reward. |
| `dashboard/components/ChainLog.js` | Table of every record stored in the contract (the shared "memory"). |
| `dashboard/components/BenchmarkChart.js` | Bar chart (library `recharts`) plus an always-visible table: Agent B's first-draft score without vs with memory, for EVERY task including regressions, computed from the per-task rows (never a hand-typed summary), with an n = 1 footnote. An optional `note` per task in `benchmark.json` is shown in the Note column. |
| `dashboard/components/CheatsTable.js` | The 5 attacks and the error the contract answered with. |
| `dashboard/components/EventLog.js` | The live log (like a terminal) and Agent B's "INJECTING LESSON" lines. |
| `dashboard/components/ui.js` | Small shared pieces: cards, coloured badges, the 3-second polling helper. |

## Words to know
- **Execution tree**: the history of one run, from the first draft to the reward.
- **Public signals**: the 16 numbers the ZK proof makes public (12 metrics, prompt commitment, snapshot hash, wallet, task). Everything else stays secret.
- **CID**: the address of the run file on IPFS. Same content always gives the same CID.
- **Record**: one entry stored in the smart contract after a proof was accepted.

## How to explain this to judges (3 sentences)
This is the developer view of the protocol: every version, every diff, every proof and every on-chain memory record, updating live.
Judges can click any run and follow it from the first draft, through the critic's feedback and the code diffs, to the ZK proof and the reward transaction on Etherscan.
The dashboard only reads public files and the public contract; it holds no keys, so what you see is exactly what anyone could verify themselves.
