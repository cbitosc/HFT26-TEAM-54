# P2 explained: ZK + attestation (plain English)

Status: real circuit done (compiled, tested, set up in `zk/out/`); `prove.js`, `make_fixture.js`, `attest/` (digest, sign, digest test) and the cheat demo (`cheat_demo.js`, `run_cheats_local.sh`) done and tested end to end on a local Anvil chain with P3's real contract. The cheat demo has NOT yet been run against a real testnet.

### zk/circuits/ and zk/out/ (the real circuit)
| File | What it does |
|---|---|
| `circuits/autoevolve.circom` | The real circuit (799 constraints, 16 public signals in PLAN.md section 3.5 order). It checks: every metric is 0-100, the score uses the fixed weights 50/20/15/15, scores strictly rise V1 < V2 < V3, and we know the secret prompt behind the public commitment (Poseidon). snapshotHash, agentWallet and taskId are tied into the proof so it cannot be reused for another run, wallet or task. |
| `test_circuit.js` | 11 witness-only tests (2 must succeed, 9 must be rejected) that also check the public-signal order. Run `node zk/test_circuit.js`. |
| `out/autoevolve.wasm` | The program that turns inputs into a witness. `prove.js` needs it. |
| `out/autoevolve_final.zkey` | The proving key (357 KB). Needed to make proofs. |
| `out/verification_key.json` | The public checking key (16 public inputs). |
| `out/Verifier.sol` | The on-chain checker, contract `Groth16Verifier`, `verifyProof(uint[2] pA, uint[2][2] pB, uint[2] pC, uint[16] pubSignals)`. |
| `prove.js` | Run as `node zk/prove.js runs/<id>`. Reads `run.json`, `secret.json` and `evaluator.json`. First it cross-checks: the evaluator's metrics must equal the ones in `run.json`, and the hash of the exact `run.json` bytes must equal the evaluator's `snapshot_hash`. Then it builds the Groth16 proof, checks it locally, and writes `proof.json` (pA, pB, pC and the 16 public numbers, all decimal strings, already in the order Solidity wants) plus one `prover` line in `events.jsonl`. If the scores do not rise it prints `CANNOT PROVE: score did not improve`. It never prints the secret prompt hash or salt. |
| `make_fixture.js` | Run as `node zk/make_fixture.js runs/<id>`. Turns a proved run into `out/fixture/fixture.json`, a ready-made valid proof for P3's Foundry tests. Agent address, task id and test-suite hash can be given as flags or environment variables (otherwise they come from the run and from the real `tasks/t<id>/tests.json`). It refuses a wallet or task that the proof was not made for, and checks its own output against the verification key. |
| `out/fixture/fixture.json` | The current fixture: Agent A (`0xdF6D...3531`), task 1, the real test-suite hash, and a proof that verifies. Changing the task id makes it fail. |
| `cheat_demo.js` | Run as `node zk/cheat_demo.js`. Tries 5 cheating attacks on the deployed contract and writes `runs/cheats.json` (for the dashboard) plus `runs/cheats.events.jsonl` (cleared at the start of every run). See "The cheat demo" below. |
| `run_cheats_local.sh` | Run as `bash zk/run_cheats_local.sh`. Starts a fresh local Anvil chain, deploys P3's contracts with `pipeline/deploy.sh 1 2 3 4`, runs the cheat demo, and finally stops Anvil and puts P3's two tracked files (`schemas/deployments.local.json`, `schemas/abi/AutoEvolveRegistry.json`) back exactly as committed, even if something fails. |

## What each file does

| File | What it does |
|---|---|
| `toy/toy.circom` | The practice circuit. It says: "I know two numbers a and b (0-255) where a < b." `a` and `b` are public. If the claim is false, no proof can be made. |
| `toy/input.json` | The sample numbers we prove with: a = 3, b = 10. |

| `toy/out/proof.json` | A sample proof for a = 3, b = 10. |
| `toy/out/public.json` | The public values for that proof: `["3", "10"]`. |
| `toy/out/calldata.txt` | The proof and public values formatted so they can be pasted straight into `verifyProof`. |

### attest/ (the evaluator's signature)
The ZK proof says the numbers are consistent. The signature says they are TRUE: it comes from the evaluator, who ran the hidden tests itself.
| File | What it does |
|---|---|
| `digest.py` | Builds the exact fingerprint (the "digest") that gets signed, from chain id, registry address, task id, agent wallet, the 12 metrics, the snapshot hash and the test-suite hash, in the frozen PLAN.md section 3.6 order. `sign_digest` signs it in the Ethereum "signed message" form that the contract checks. |
| `test_digest.py` | Checks `digest.py` against P3's example: the example signature recovers to the example evaluator address, signing with that address's public Anvil test key gives the identical signature, and changing any one of the 7 inputs changes the digest. Run `python -m attest.test_digest`. |
| `sign.py` | Run as `python -m attest.sign --run runs/<id>`. It RE-RUNS the hidden tests for V1, V2 and V3 itself and **refuses to sign if any metric differs from `run.json`** (there is no flag to skip this). It also checks the test-suite hash against the real `tasks/t<id>/tests.json`, takes chain id and registry from `load_deployment()`, signs with `EVALUATOR_PRIVATE_KEY` from `.env` (never printed), writes `evaluator.json` and adds an `evaluator` line to `events.jsonl`. `--chain-id` and `--registry` exist for local testing only and print a loud warning. |

## The cheat demo (5 attacks, plus one honest check)
The contract's `submit()` runs its checks in a fixed order: known task, right task, right wallet, not claimed yet, valid proof, evaluator signature. Each attack is set up to pass every EARLIER check, so the rejection we see is the one the attack is really about. Four of the five are tried against the real contract; attack 1 never reaches it, because the proof cannot even be built.
| # | Attack | What the cheater tries | What stops it | What it proves |
|---|---|---|---|---|
| 1 | `score_down` | Claim an improvement when the third score is really lower than the second. | The circuit rule "each score is higher than the last": no proof can be built (`CANNOT PROVE`). | The scoring rule is enforced by mathematics, not by trusting the agent. |
| 2 | `forged_metrics` | Build a valid proof, then quietly change one public number afterwards. | The contract's proof check (`BAD_PROOF`): a proof only fits the exact numbers it was made for. | Numbers cannot be edited after proving. |
| 3 | `stolen_proof` | Agent B copies Agent A's valid proof and submits it to grab the reward. | `NOT_AGENT`: Agent A's wallet is baked into the proof and must equal the sender. | A proof cannot be stolen or front-run. |
| 4 | `replay` | Agent A is paid for task 1, then submits the same thing again for a second payment. | `ALREADY_CLAIMED`: one payment per agent per task. | No double payouts. |
| 5 | `invented_metrics` | Invent impressive numbers, build a perfectly VALID proof for them, and "sign" them with a random wallet. | `BAD_EVALUATOR_SIG`: the contract only accepts the named evaluator's signature. | A proof says the numbers are consistent, not that they are true; the evaluator's signature is what says they are true. |

**Why attack 5 matters most.** The mathematical proof is completely valid there: the invented numbers really are in range, use the fixed weights and rise. The contract still rejects it, because the real evaluator never re-ran the tests and never signed those numbers. This is the whole reason we have two layers: the zero-knowledge proof checks the rules, and the evaluator's signature supplies the truth. It also shows the limit: **the evaluator is a named trust assumption.** If the evaluator were dishonest or its key stolen, it could sign false numbers, and nothing in the proof would catch that (PLAN.md section 7).

**The rehearsal script always runs on local Anvil, whatever `.env` says.** `run_cheats_local.sh` sets the chain to local with a localhost RPC and uses Anvil's public test account as the deployer. It also runs a temporary copy of `pipeline/deploy.sh` without its `.env` loading, because that script would otherwise override those settings and, with `CHAIN=sepolia`, deploy to Sepolia. It was tested with `CHAIN=sepolia RPC_URL=https://invalid.example` and still ran entirely locally. At the end it restores P3's two tracked schema files.

**Read-only mode on Sepolia needs task 1 claimed first.** Attack 4 replays an existing claim, so Agent A must already have claimed task 1 on that chain by a real transaction made with the normal pipeline; until then the demo refuses with a clear message and sends nothing. On Sepolia today a dry-run `submit()` for task 1 succeeds (unclaimed), and tasks 2 and 3 are unclaimed, as attacks 2 and 5 need.

**Run order matters.** Every run overwrites `runs/cheats.json` and `runs/cheats.events.jsonl`, so do the local rehearsal first and the Sepolia read-only run LAST: the files the dashboard reads should come from the run you want to show.

**Honest check.** A valid proof with the real evaluator's signature on an unclaimed task must NOT be rejected. The demo does this first (a dry run, no transaction) so we know the contract is not simply rejecting everything.

**Two modes.** On a fresh local chain (id 31337) the demo does ONE real transaction: Agent A's genuine claim for task 1, so attack 4 has a real payment to replay. It checks that the payment arrived (reward minus gas) before replaying. On any other chain, or with `READ_ONLY=1`, it is read-only: it never deploys, never sends a transaction and never changes balances, uses dry-run calls only, and insists that Agent A already claimed task 1, that tasks 2 and 3 are registered and unclaimed by Agent A, and that the contract's evaluator is not the zero address (otherwise the signature check is switched off and attack 5 could not be rejected). It skips the honest check, which needs a real signed run. `run_cheats_local.sh` also checks that read-only mode refuses when nothing is claimed yet, and then runs the read-only mode on the same local chain and confirms it sent 0 transactions.

## How the toy was made (the pipeline in 6 steps)
1. Write the rule in circom (`toy.circom`).
2. Compile it to constraints and a witness program (`circom`).
3. Setup: combine the circuit with the ptau file to make a proving key and a checking key (`snarkjs groth16 setup`, then one `zkey contribute`).
4. Prove: give private/public inputs, get a small proof (`snarkjs groth16 fullprove`).
5. Verify: check the proof with only the checking key (`snarkjs groth16 verify` printed `OK!`).
6. Export the checking key as a Solidity contract so a blockchain can do step 5.

Negative test: with a = 10, b = 3 the witness generator stops with `Assert Failed` at the line `lt.out === 1`. No witness means no proof, so a false claim cannot be proven.

## Honest notes (say these if asked)
- **The trusted setup was run entirely by us, with one contributor per phase.** The official public Hermez "Powers of Tau" file (`powersOfTau28_hez_final_12.ptau`) returned HTTP 403 from both download URLs on 2026-10-30 (retried with a browser User-Agent), so we generated phase 1 ourselves with snarkjs (`pot12_local_final.ptau`), and then ran phase 2 for our circuit (`zkey contribute`), also with one contribution of random bytes from this laptop. The maths and file formats are the same as the official route, but the trust is weaker: anyone who had kept the secret randomness from either phase could in theory forge proofs. That is fine for a hackathon demo. Production would use the public Hermez ceremony (many independent contributors) plus a multi-party phase 2, where only one honest participant is needed for safety.
- The toy verifier (`zk/toy/out/`) checks 2 public signals; the real one (`zk/out/Verifier.sol`) checks 16.
- Tamper test passed: a real proof verifies (`OK!`), and changing one public signal (V3 metric 100 to 99) makes the same proof fail (`Invalid proof`).
- **The evaluator is a named trust assumption** (PLAN.md section 7). The proof guarantees the numbers are in range, use the fixed weights and rise; the signature guarantees the evaluator, who re-ran the tests, vouches for them. We do not prove the test run itself in zero knowledge.
- **A signature made with `--chain-id` / `--registry` overrides is for testing only** and will not verify against the real deployment. Real signing needs P3's `schemas/deployments.<CHAIN>.json`.
- **`sign.py` depends on the pinned lint tools** (`ruff==0.17.3`, `radon==6.0.1` in `requirements.txt`). With other versions the re-run could disagree with the agent's numbers and `sign.py` would refuse an honest run. Install exactly the pinned versions.
- The fixture's example signer is Anvil account #1 (`0x7099...`), not the real evaluator (`0xeC9D...` in `schemas/addresses.json`); the example is only a test vector.
- **The cheat demo has only been run on a local Anvil chain** with the real verifier and registry. Its read-only mode was self-tested on that local chain (0 transactions, all 5 attacks rejected) but has not been run against Sepolia or Base Sepolia. It needs Foundry, `npm ci` inside `contracts/`, and the `.venv` that `pipeline/deploy.sh` uses.
- The cheat demo's local run funds the deployer account on the throwaway Anvil chain if it is empty. That is a local-chain-only convenience and is never done elsewhere.
- `docs/roles/P2.md` is still a placeholder from P3, so steps were taken from the task message and PLAN.md.

## How to explain this to judges (3 sentences)
A zero-knowledge proof lets our agent show that its scores really improved from version 1 to 2 to 3, using our fixed scoring formula, without revealing its secret system prompt, and a smart contract can check that tiny proof in one call. Separately, an independent evaluator re-runs the hidden tests itself, refuses to sign if even one number differs from what the agent claimed, and signs only the numbers it reproduced, so the agent's word is never taken on trust. We tested both halves, including five cheating attempts against the real contract on a local test chain (a falling score, a forged number, a stolen proof, a replayed claim, and invented metrics signed by the wrong party): every attack was rejected while an honest submission was accepted.
